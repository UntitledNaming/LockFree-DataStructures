# Design Rationale

이 문서는 "왜 이렇게 설계·판단했는지"를 정리합니다. 각 항목은 문제 상황 / 선택한 방식 / 대안 / 선택 이유 / 절충 / 검증 방법 순으로 적습니다. 코드 흐름의 상세는 `docs/Code_Flow.md`를 참고하세요.

---

## 1. 왜 Lock-Free 자료구조를 직접 구현했는가

- 문제 상황: 게임 서버는 본질적으로 멀티스레드 환경이라, 세션 큐·메시지 풀·작업 큐 같은 공유 자료구조에서 동시성 문제를 이해·해결하는 능력이 필요하다.
- 선택한 방식: Lock-Free 스택·큐·메모리 풀을 직접 구현하고, 실제로 터지는 문제 4종을 재현·해결한다.
- 대안: 표준/서드파티 락프리 컨테이너를 그대로 사용.
- 선택 이유: 라이브러리를 쓰기만 하면 내부에서 왜 문제가 나는지 알 수 없다. 직접 구현하고 문제를 재현해야, 이후 실제 서버(세션 송신 큐, 메시지 풀 등)에 안전하게 적용할 근거가 생긴다.
- 감수한 점: 구현·검증 난이도가 매우 높다(CAS 재시도, 메모리 회수).
- 검증 방법: 문제별 재현/해결 테스트, 동기화 비교 테스트.
- 관련 코드 흐름: 전체.
- 관련 테스트/트러블슈팅: 4대 문제, 동기화 비교.
- 확인 필요: 없음.

## 2. 왜 ABA 문제가 발생하는가

- 문제 상황: Pop이 top과 top->next를 읽은 사이, 그 노드가 반환·재사용되어 top이 A→B→A로 돌아온다.
- 선택한 방식(분석): 주소만 비교하는 CAS의 한계를 인정한다.
- 선택 이유: CAS는 "현재 포인터 값이 내가 읽은 값과 같은가"만 본다. 메모리가 재사용되면 같은 주소가 다시 등장하는데, 그 사이 상태(next)가 바뀌었어도 CAS는 성공해버린다. 즉 현재 포인터 값만으로는 그 사이 어떤 이벤트가 있었는지 알 수 없다.
- 감수한 점: 주소 비교만으로는 안전하지 않아 추가 정보가 필요하다.
- 검증 방법: 태그 없는 CAS 스택으로 ABA를 재현하고 로그로 시퀀스를 추적.
- 관련 코드 흐름: Lock-Free Stack, ABA 재현/해결.
- 관련 트러블슈팅: ABA 문제.
- 확인 필요: 없음.

## 3. 왜 version/tagged pointer가 필요한가

- 문제 상황: 같은 주소 재사용을 CAS가 구분하지 못한다.
- 선택한 방식: 포인터 상위 비트에 단조 증가 버전 카운터를 실어 "주소 + 버전"을 함께 비교(태그드 포인터).
- 대안: 128비트 CAS로 포인터+버전을 별도 저장, Hazard Pointer 등.
- 선택 이유: 유저 모드 주소는 상위 비트가 비어 있어, 그 자리에 버전을 실으면 64비트 CAS 하나로 "주소가 같아도 버전이 다르면 실패"를 만들 수 있다. 스택에는 이 방식이 간결하다.
- 감수한 점: 태그 비트폭이 제한적이라 카운터가 순환할 수 있고(현실적으로는 충분), 마스크 처리가 필요하다.
- 검증 방법: 해결판 스택으로 같은 재현 시나리오를 통과.
- 관련 코드 흐름: Lock-Free Stack, ABA 해결.
- 확인 필요: 없음.

## 4. 왜 Page Decommit은 ABA 카운터만으로 해결되지 않는가

- 문제 상황: 노드 페이지가 OS에 반환된 뒤, 다른 스레드가 그 주소를 참조해 크래시한다.
- 선택한 방식(분석): ABA와 Page Decommit은 다른 문제임을 구분한다.
- 선택 이유: ABA는 "같은 주소가 재사용되는" 문제라 버전 카운터로 구분할 수 있다. Page Decommit은 "참조 중인 메모리 자체가 OS에 반납되는" 문제다. 버전 카운터는 재사용 여부만 볼 뿐, 그 메모리가 아직 살아 있는지(생존 기간)는 보장하지 못한다. 메모리가 사라지면 카운터를 읽는 순간 이미 크래시다.
- 감수한 점: 메모리 회수 정책을 별도로 마련해야 한다.
- 검증 방법: 페이지를 OS에 반환하는 재현판으로 크래시를 재현하고, 자체 풀 해결판으로 통과.
- 관련 코드 흐름: Page Decommit 재현/해결.
- 관련 트러블슈팅: Page Decommit 문제.
- 확인 필요: 없음.

---

## 5. 왜 노드 메모리 재사용 정책이 중요한가

- 문제 상황: Lock-Free 구조에서 Pop 이후 노드를 반환하는 타이밍에, 다른 스레드가 여전히 그 노드를 참조 중일 수 있다.
- 선택한 방식: 노드를 OS에 반환하지 않고 자체 메모리 풀에 보존·재사용한다.
- 대안: 즉시 free(OS 반환), Hazard Pointer, Epoch Based Reclamation.
- 선택 이유: 락프리는 "읽은 포인터가 언제든 유효"해야 한다. 노드를 OS로 돌려주지 않으면 주소가 사라지지 않아 dangling 접근을 원천 차단한다. 풀은 재사용도 빠르다.
- 감수한 점: 풀에 노드가 상주해 메모리 사용량이 늘고, 재사용으로 인한 ABA는 별도로(태그로) 막아야 한다.
- 검증 방법: Page Decommit 해결판, 반복 Push/Pop 테스트.
- 관련 코드 흐름: 메모리 풀, Page Decommit 해결.
- 확인 필요: 없음.

## 6. 왜 Shared Node Pool에서 Qid + CAS128이 필요한가

- 문제 상황: 여러 큐가 같은 노드 풀을 공유하면, 한 큐가 반환한 노드를 다른 큐가 재사용하면서 소유가 혼동될 수 있다.
- 선택한 방식: 노드에 소유 큐 식별자(Qid)를 심고, 링크를 128비트 CAS로 바꿔 `(next, Qid)`를 함께 검증.
- 대안: 큐마다 독립 풀 사용.
- 선택 이유: 링크 CAS가 next만 보면, 그 노드가 내 큐 것인지 남의 큐 것인지 알 수 없다. Qid를 함께 비교하면 남의 큐 노드는 CAS가 실패해 거부된다. 128비트 CAS는 포인터(next)와 식별 정보(Qid)를 원자적으로 함께 확인할 수 있다.
- Enqueue/Dequeue에서 태그 필요 여부(실제 코드 기준): 멀티 버전은 head/tail 포인터 CAS에 카운터 태그를 Enqueue(tail)와 Dequeue(head, tail) 모두에 적용하고, 노드 링크(`_next`)에는 태그 대신 Qid+CAS128을 쓴다. 즉 링크 오염은 태그가 아니라 Qid로 막는다.
- 감수한 점: 128비트 CAS 비용과 Qid 관리가 추가된다.
- 검증 방법: 공유 풀 오염 재현판(CAS64, Qid 없음)과 해결판(Qid+CAS128) 비교.
- 관련 코드 흐름: Shared Node Pool 오염 재현/해결.
- 관련 트러블슈팅: Shared Node Pool 오염 문제.
- 참고: "Enqueue에는 태그가 불필요하다"는 초기 판단은 이후 번복되었다. tail을 밀어주는 사전 작업에서 tail 변화 감지를 위해 태그가 필요함을 확인했다 — 최종 정리는 §10 참고.

## 7. 왜 Lock-Free가 항상 빠르지 않다고 판단했는가

- 문제 상황: "락프리는 락이 없으니 항상 빠르다"는 통념이 실제로 맞는지 확인해야 한다.
- 선택한 방식: Spinlock / SRWLock / Lock-Free를 스레드 수별로 비교.
- 선택 이유: 락프리는 경합이 심하면 CAS 실패 재시도가 늘어 오히려 손해일 수 있고, 메모리 재사용 문제도 함께 안는다. 반면 SRWLock은 대기 시 스케줄러에 양보하고, Spinlock은 짧은 임계구역에 유리하다. 스레드 수와 경합 구조에 따라 우열이 달라졌다.
- 감수한 점: 어느 하나로 고정하면 특정 조건에서 손해다.
- 검증 방법: 스레드 1/3/16 등에서 Total Count·성공/실패·CPU 비교.
- 관련 코드 흐름: 동기화 방식 비교 테스트.
- 관련 테스트/트러블슈팅: 동기화 비교, 측정 이슈.
- 확인 필요: 스레드 수별 실측 수치는 정리 중(TODO).

## 8. 왜 성능 비교 지표를 Total Count로 잡았는가

- 문제 상황: 동기화 방식을 비교할 공정한 지표가 필요하다.
- 선택한 방식: 정해진 시간 동안 처리한 작업 횟수(Total Count)를 지표로 삼고, 함께 시도/성공/실패 비율과 CPU·컨텍스트 스위치도 기록.
- 대안: 단일 연산 지연(latency)만 측정.
- 선택 이유: 같은 시간 동안의 처리량이 방식 비교에 직관적이다. 절대 수치 자체보다, 스레드 수와 경합 조건이라는 비교 조건이 더 중요하다는 관점이다.
- 감수한 점: 처리량만으로는 꼬리 지연을 못 보므로, 성공/실패 비율과 CPU를 함께 본다.
- 검증 방법: 스레드 수별 결과 파일 비교.
- 관련 코드 흐름: 동기화 방식 비교 테스트.
- 확인 필요: 실측 수치는 정리 중(TODO).
