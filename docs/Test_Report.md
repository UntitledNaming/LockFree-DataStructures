# Test Report

이 문서는 Lock-Free 자료구조의 동작 검증, 4대 동시성 문제의 재현/해결 검증, 동기화 방식 비교를 정리합니다. 확정된 수치만 사용하고, 아직 판독·정리되지 않은 정량 값은 TODO로 표시합니다.

## 1. 테스트 목적

- **정상 동작 확인**: Lock-Free 스택·큐가 다수 스레드에서 정합성 있게 동작하는지 확인.
- **동시성 문제 재현**: ABA·Page Decommit·Order Reversal·공유 풀 오염을 의도적으로 재현.
- **해결 코드 검증**: 해결 코드가 같은 재현 시나리오를 통과하는지 확인.
- **동기화 방식 비교**: Spinlock / SRWLock / Lock-Free를 스레드 수별로 비교.
- **부하 조건/경합 조건별 성능 차이 확인**: 어느 방식이 항상 우위가 아니라, 조건에 따라 달라짐을 확인.

## 3. 동기화 방식 비교

- Spinlock: 짧은 임계구역에 유리하고, 대기 중 CPU를 소모한다. 스레드가 논리 코어 수를 넘어서면 상대적으로 불리해지는 경향이 있다.
- SRWLock: OS가 제공하는 락으로, 대기 시 스케줄러에 양보한다. 테스트한 조건에서 안정적인 처리량 경향을 보였다.
- Lock-Free: 락 없이 CAS로 진행해 대기가 없지만, 경합이 심하면 CAS 실패 재시도 비용이 커진다.
- Total Count 기준 비교: 정해진 시간 동안 처리한 작업 횟수를 비교했고, 함께 시도/성공/실패 비율과 CPU·컨텍스트 스위치를 기록했다.
- 스레드 수에 따른 변화: 논리 코어 수와 스레드 수의 관계에 따라 방식별 순위가 달라지는 경향을 관측했다(예: 스레드 수가 코어 수를 넘느냐에 따라 상대 우열이 바뀜).
- 결과 해석: "Lock-Free가 항상 가장 빠르다"가 아니라, 부하 조건·경합 구조·스레드 수에 따라 유리한 방식이 달라진다.

> 각 방식·스레드 수 조합의 구체 수치(Total Count·성공률·CPU)는 `docs/results/`의 결과 파일 판독 후 채웁니다. 위 경향은 관측 방향이며, 정량 값은 확정 전까지 단정하지 않습니다. (TODO)

## 4. 로그 기반 검증

- 로그를 남긴 이유: 동시성 버그는 크래시가 난 "현재 상태"만 봐서는 원인을 알기 어렵다. 어떤 스레드가 어떤 순서로 top/next를 읽고 CAS했는지 이벤트 순서를 알아야 한다.
- 방법: 각 시도의 지역 값(top, next), 스레드 ID, 순번을 링 버퍼에 기록하고(예: 스택의 로그 캡처), 문제가 감지되면 파일로 덤프해 시퀀스를 되짚는다. 메모리 풀의 소유 ID 불일치·이중 반납이 감지되면 그 지점에서 중단·기록한다.
- 이벤트 시퀀스 추적의 필요성: A→B→A 같은 재사용은 시퀀스를 봐야 보인다. 상태 스냅샷만으로는 "왜 CAS가 성공했는지" 설명되지 않는다.
- 관련 자료: `debug_cases/ABA/`(ABA 로그 분석), `debug_cases/2nd CAS 실패 문제점 분석/`(순서 꼬임 케이스).
- 확인 필요: 예외 처리에 SEH(구조적 예외 처리)를 사용했는지는 코드에서 명시적으로 확인하지 못했다. 재현 코드는 조건 위반 시 중단(break) + 로그 덤프 방식을 사용한다. (SEH 사용 여부 확인 필요)

---

## 5. 결론

- 동시성 문제는 현재 상태가 아니라 이벤트 순서를 추적해야 원인이 보인다.
- Lock-Free는 성능 이점만이 아니라 메모리 재사용(ABA·Page Decommit·공유 풀 오염) 문제를 함께 다뤄야 한다.
- 동기화 방식은 어느 하나가 항상 우위인 것이 아니라, 부하 조건·경합 구조·스레드 수에 따라 선택해야 한다.

> 문제별 추적·해결 과정의 상세는 `docs/Troubleshooting.md`를 참고하세요.
