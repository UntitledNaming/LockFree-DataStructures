# Test Report

이 문서는 Lock-Free 자료구조의 동작 검증, 4대 동시성 문제의 재현/해결 검증, 동기화 방식 비교를 정리합니다. 확정된 수치만 사용하고, 아직 판독·정리되지 않은 정량 값은 TODO로 표시합니다.

---

## 1. 테스트 목적

- **정상 동작 확인**: Lock-Free 스택·큐가 다수 스레드에서 정합성 있게 동작하는지 확인.
- **동시성 문제 재현**: ABA·Page Decommit·Order Reversal·공유 풀 오염을 의도적으로 재현.
- **해결 코드 검증**: 해결 코드가 같은 재현 시나리오를 통과하는지 확인.
- **동기화 방식 비교**: Spinlock / SRWLock / Lock-Free를 스레드 수별로 비교.
- **부하 조건/경합 조건별 성능 차이 확인**: 어느 방식이 항상 우위가 아니라, 조건에 따라 달라짐을 확인.

## 3. 동기화 방식 비교 (2026-07 재측정)

### 3.1 측정 환경
- 같은 작업(스택 Push+Pop 1회 = 1루프)을 세 방식으로 3분간 반복, Total Count(처리량)와 interlock 시도/성공/실패, CPU user/kernel, 컨텍스트 스위치/초를 기록.
- 논리 12코어(물리 6코어 + 하이퍼스레딩). 스레드 6개 이하는 서로 다른 물리 코어에 어피니티 고정, 36개는 OS 스케줄링.
- 계측 개선: 스레드별 카운터를 alignas(64)로 분리해 계측 카운터끼리의 거짓 공유 제거, 성공·실패 개념이 없는 무조건 RMW(topCnt 증가·unlock)는 별도 카운터로 분리해 성공률 분모 오염 방지. 구버전(10초, 스레드 1/3/16) 결과는 이 문제로 폐기하고 전면 재측정.

### 3.2 결과 (3분 Total Count, 대표값)

| 스레드 | SRWLock | Spinlock | Lock-Free |
|:---:|---:|---:|---:|
| 1 | 약 73억 | 약 74억 | 약 63억 |
| 3 | 약 50억 | 약 12억 (성공률 ~11%) | 약 8.2억 (성공률 70~76%) |
| 6 | 약 30억 | 약 11.5억 (성공률 10~12%) | 약 6.5억 (성공률 50~60%) |
| 36 | 약 24억 | 약 3.0억 (성공률 ~2.2%) | 약 5.9억 (성공률 80~89%) |

- 세 방식 모두 CPU는 스레드 수만큼 user 영역에서 완전 소모(kernel ≈ 0%), 코어 이하 구간 컨텍스트 스위치는 초당 수십 회 → 처리량 차이는 코어가 러닝 상태로 캐시라인을 기다린 시간의 차이.

### 3.3 분석
- 단일 스레드: lock 명령어(xchg)와 CAS의 명령 자체 부하는 별도 테스트로 차이가 거의 없음을 확인. Lock-Free가 13%쯤 낮은 것은 루프당 원자 연산 개수 차이(락 2회 vs 락프리 4회).
- 코어 이하(3·6개): Spinlock은 실패한 시도도 캐시라인을 뺏어오기 때문에 3스레드에 이미 같은 캐시라인 locked RMW의 상한에 포화(3→6개에서 성공률·총량 불변). Lock-Free는 성공률이 높은데도 성공한 연산마다 top·topCnt 캐시라인을 자기 코어로 끌어와야 해 열세. SRWLock은 백오프(RtlBackoff)와 wait block 로컬 스핀으로 캐시라인 이동을 아껴 최상.
- 검증 실험: Spinlock에 지수 백오프(pause + 실패 시 2배)를 이식 → 3스레드 12억 → 46억(성공률 11%→81%), SRWLock(50억)에 근접. 같은 백오프가 Lock-Free에선 효과 없음(8억대 유지) → 두 방식의 병목이 다름을 분리 검증. (`SpinLock에 backoff 추가한 코드/`, `LockFree에 backoff 추가한 코드/`)
- 코어 초과(36개): 컨텍스트 스위치가 초당 1,400~3,700회로 증가. Spinlock은 락 보유 스레드 선점으로 붕괴(성공률 2%), Lock-Free는 진행 보장으로 완만히 하락해 Spinlock을 역전, SRWLock은 대기자의 커널 양보로 수성.
- 결론: 코어 이하 구간은 공유 캐시라인 이동 횟수가, 코어 초과 구간은 스케줄러 개입에 대한 내성이 우열을 가른다. "Lock-Free가 항상 빠르다"는 성립하지 않는다.

## 4. 로그 기반 검증

- 로그를 남긴 이유: 동시성 버그는 크래시가 난 "현재 상태"만 봐서는 원인을 알기 어렵다. 어떤 스레드가 어떤 순서로 top/next를 읽고 CAS했는지 이벤트 순서를 알아야 한다.
- 방법: 각 시도의 지역 값(top, next), 스레드 ID, 순번을 링 버퍼에 기록하고(예: 스택의 로그 캡처), 문제가 감지되면 파일로 덤프해 시퀀스를 되짚는다. 메모리 풀의 소유 ID 불일치·이중 반납이 감지되면 그 지점에서 중단·기록한다.
- 이벤트 시퀀스 추적의 필요성: A→B→A 같은 재사용은 시퀀스를 봐야 보인다. 상태 스냅샷만으로는 "왜 CAS가 성공했는지" 설명되지 않는다.
- 관련 자료: `debug_cases/ABA/`(ABA 로그 분석), `debug_cases/2nd CAS 실패 문제점 분석/`(순서 꼬임 케이스).
- 확인 필요: 예외 처리에 SEH(구조적 예외 처리)를 사용했는지는 코드에서 명시적으로 확인하지 못했다. 재현 코드는 조건 위반 시 중단(break) + 로그 덤프 방식을 사용한다. (SEH 사용 여부 확인 필요)

---

## 5. 결론

- 동시성 문제는 현재 상태가 아니라 이벤트 순서를 추적해야 원인이 보인다.
- Lock-Free는 성능 이점만이 아니라 메모리 재사용(ABA·Page Decommit·공유 풀 오염) 문제를 함께 다뤄야 한다.
- 동기화 방식은 어느 하나가 항상 우위인 것이 아니라, 부하 조건·경합 구조·스레드 수에 따라 선택해야 한다.
