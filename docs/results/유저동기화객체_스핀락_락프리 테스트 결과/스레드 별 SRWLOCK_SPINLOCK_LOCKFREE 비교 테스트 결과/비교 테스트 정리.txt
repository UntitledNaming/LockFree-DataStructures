2. 단일 스레드에서 lockfree, spinlock, srwlock 차이
- spinlock과 srwlock은 그냥 interlock 걸어봐야 어차피 다른 스레드 없으니 바로 소유권 얻어서 push, pop을 하고 interlock으로 소유권 해제함.
- 근데 lockfree는 성능 차이가 약간 존재함. 
- 처음에는 lock과 cas의 명령어 자체 부하 차이인가 싶어서 별도 코드를 삽입해 하나는 3분동안 interlockexchange 2번을 계속 반복하고 락프리는 cas를 2번 반복하게 테스트함.
  그것이 1번의 결과임. 보다 시피 차이가 거의 없음.
- 그러면 이런 차이가 발생한게 다른 원인인데 lockfree stack을 보면 cas 이외에도 interlock으로 topCnt를 할당받아야 함. 이걸 1번의 작업(push, pop)을 할때 2번 interlock을 하기 때문에
  다른 spinlock이나 srwlock과 달리 interlock이 1번의 루프에서 2번이 더들어감. 이것 때문에 lockfree의 성능이 좀 떨어진것으로 판단함.
- 단일 스레드에서 interlock 좀 넣었다고 이런 차이가 나는거면 interlock 자체에 어떤 부하가 있길래 이런 차이가 있는지 봐야 함.

-  interlock 없었으면 store 명령어들 어차피 그냥 실행은 어차피 비순차고 이제 커밋 단계는 그냥 스토어 버퍼에 기록만 땅땅 하는건데
   lock이 들어가면서 기록만 하는게 아니라 캐시 메모리까지 접근해서 반영해야 해서 시간이 더 걸리게 되지 않나 싶은거임

3. 스레드 3개 생성후 lockfree, spinlock, srwlock 차이
- srwlock 50억 > spinlock 10억 > lockfree 8 억임
- 이것의 원인을 생각해보니 srwlock의 경우 경합 실패하면 바로 다시 lock 명령어로 소유권 획득 시도 하는게 아니라 중간 중간 backoff에서 spin 돌다가 한번 lock 시도 하는 방식 취하다가
  최종적으로 block되고 spinlock의 경우 lock 획득 실패하면 바로 다시 interlock을 시도 함. 
- 이게 여러 스레드가 lock을 시도하는데 만약 동시에 lock 명령어 처리를 한다면 한 코어가 캐시 라인 소유 하는 동안에는 다른 코어는 러닝 상태에서 계속 대기함. 그 코어가 캐시라인 잠근거 풀때까지.
- 또한 spinlock은 실패하면 다시 루프돌아서 interlockexchange를 통해 캐시라인을 다시 독점적으로 가져오게하고 다른 코어 캐시라인 무효화 시키고 이것 때문에 spinunlock할때 캐시라인 무효화 되어 있으니 캐시라인을 
  다른 캐시 메모리에서 가져오는 딜레이가 생김. 또한 실패한 스레드끼리 계속 캐시라인 독점적으로 가져와서 다른 코어 캐시 메모리 무효화 시키고 플래그를 바꿔주는데 의미도 없는데 계속 캐시 라인 무효화 시켜서 
  실패한 다른 스레드가 interlockexchange하는것도 오래걸리게 하고 lock  소유한 스레드가 lock 푸는것도 오래걸리게 하는 영향이 있음. 
- 그래서 SpinLock에도 backoff 기능을 넣어서  interlock으로 소유권 획득 시도 실패하면 바로 다시 interlock 시도하는게 아니라 약간의 for 문 돌면서 srwlock처럼 pause를 시도하고 도는 횟수를 지수함수적으로 증가시킴. 
- 그래서 backoff 기능을 넣고 spinlock을 다시 테스트해보면 srwlock처럼 46억 정도의 성능이 도출됨.
- lock을 통해 소유권 확보 하는 시도를 어떻게 보면 스레드 마다 분산을 시킨 것임. 분산 시켜서 여러 스레드가 동시에 lock 명령어 처리 들어가서 대기 하는 상황이 나오지 않게 최대한 막은 것임. 그러니 srwlock 처럼 성능이 꽤 올라왔음.

- lockfree의 성능 저하 원인이 spinlock과 같이 cas or lock 실패 후 다시 cas or lock 시도 하면서 lock 대기 하는거였다면 애초에 lockfree에서 interlock 성공률이 spinlock 처럼 낮았을 것임. 그래서 부하 원인이 이것이 아니라 다른 것임.
  경합이 존재할때 topCnt 할당하기 위해 interlock 사용하면서 내 캐시라인에 기록하면서 다른 캐시라인 invalid하면서 다른 스레드가 topCnt할당할때 캐시라인 가져와야 하는 딜레이도 있음. 
- lockfree는 성공률도 높음. 대신 결국 topCnt 할당할때 interlock 2번 더 해야 하는 부하(스토어 버퍼 플러시 , 캐시라인 독점 문제 ) + cas 성공률이 높으니 결국 cas를 통해 내 캐시라인 수정하고 다른 캐시라인 invalid 만드니 
  그 코어가 cas 처리할때 캐시라인 계속 가져와야 하는 부하 같은게 있음.

4. 스레드 6개 생성후 lockfree, spinlock, srwlock 차이
- 결과를 비교하면 srwlock 30억 > spinlock 10억 > lockfree 6억5천
- srwlock은 성능이 떨어졌고 spinlock은 거의 변동이 없고 lockfree는 성능이 떨어짐. 
- 락프리의 성능을 보면 성공율도 70%에서 50%로 감소함. 스냅샷 찍고 CAS하는데 뒤이어 스냅샷 찍으러 오는 스레드 갯수 자체가 증가하니 보통 이런 스레드는 CAS 실패하게 될 것임. 그래서 실패율이 증가한 것으로 생각됨.
- 스핀락을 보면 성능의 변동이 없는데 스레드 3개일 때 lock 획득 성공율을 보면 10%이고 6개일 때도 10%임. 즉, 이미 3개일때 조차 한계로 부하가 걸린 상태였단 것임.
- lock 처리하려면 캐시라인을 독점적으로 가져와서 수정하는데 이때 가져오는건 무조건 1코어만이 가져올 수 있음. 즉, 특정 시점에서 같은 캐시라인에 대해 lock 명령어 시도해서 수정할 수 있는 max치는 정해져 있는것임.
- 이게 스레드 3개일 때 이미 max치로 같은 캐시라인에 대해 lock 명령어로 수정하고 있었던 것이고 스레드가 6개 늘었어도 애초에 같은 캐시라인에 대해 lock 명령어 수정 max치는 정해져 있으니 
  그걸 3개 스레드가 나눠 가지느냐 6개 스레드가 나눠 가지느냐의 차이임.

5. 스레드 36개 생성후 lockfree, spinlock, srwlock 차이 
- 결과는 srwlock 24억 > lockfree 5.9억 > spinlock 3억
- cpu 사용률을 보면 전부다 99%유저 영역을 쓰고 있으니 스레드가 block되어서 쉬고 나서 돌아오는 상황은 없다고 할 수 있으나 애초에 코어 갯수보다 스레드 갯수가 많기 때문에 항상 코어에 스레드가 붙어서 코드가 돌고 
  다른 스레드들은 block되어 있을 수도 있음. 그래서 보면 컨텍스트 스위칭 횟수도 SRWLOCK이 높음.
- 경합의 빈도가 높아지고 중간 중간 lock먹고 나서(lockfree 제외) 컨텍스트 스위칭이 발생하는 등 이런 요인으로 인해 전체적으로 성능이 떨어진 것으로 확인됨.
- 우선 srwlock 성능 떨어진건 그렇다고 치고 spinlock이 상당히 성능이 확 떨어지고 lockfree는 그렇게 크게 떨어지지는 않았음.
- spinlock 성능 떨어진거는 interlock 성공률만 봐도 원래 10%인데 2%까지 떨어진거임. 왜냐면 내가 생각하기에 동기화 객체 소유한 스레드가 push ,pop 하고 바로 lock을 풀어줘야 하는데 lock 못 풀고 자꾸 컨텍스트 스위칭 발생하니
  lock 푸는 시간이 늦어지면서 실패율이 높아지고 성능도 떨어지는 것으로 판단 됨.
- 또한 lock 먹은 스레드 제외하고 다른 스레드들이 계속 퀀텀 다 쓸 때까지 cpu 태우면서 돌기 때문에 lock 먹은 스레드가 다시 코어 획득하는게 늦어짐.

- lockfree를 보면 6개 스레드에서 테스트했던것보다 약간 떨어지지만 성공률 자체를 보면 6개 스레드에서는 50%대인데 36개 스레드는 오히려 성공률이 80%대로 올랐음.
- lockfree에서도 결국 코어 갯수보다 만은 스레드로 인해 계속 컨텍스트 스위칭이 발생하면서 결국 push, pop이 방해되기 때문에 전체 시간에서의 count 총합은 떨어질 수 있음.
- 다만 성공률이 6개보다 올라감으로 인해 이를 상쇄한것으로 보임.

- 그러면 성공률이 어떤 요인으로 올라갔을까 생각해보자.
- 스레드 6개는 그냥 각자가 각 코어에서 돌아가면서 흘러가기 때문에 그냥 한 스레드가 지금 CAS 중인데 그 순간 스냅샷 저장하는 스레드가 나오는 빈도가 높아지게 되는거임.
- 그러나 코어 갯수 보다 많아진 스레드가 돌아가는 환경에서는 오히려 나 CAS중인데 그 순간 다른 스레드가 Push나 Pop 호출하면서 스냅샷 저장하려는데 스레드가 많으니 스냅샷 저장 못하고 컨텍스트 스위칭 되고 
  나는 그냥 바로 cas되버리고 하는 상황이 많아져서 성공률이 높아지지 않은가 싶음. 
- 추가적으로 push 할때 노드 할당도 원래는 스핀락은 lock을 먹어야지만 push할때 노드 할당을 하는데 lock 획득 후 컨텍스트 스위칭  발생으로 인해 lock 반납이 늦어지니 다른 스레드는 노드 할당 자체를 못하는데 
  락프리는 모든 스레드가 각자 노드 할당을 독자적으로 하기 때문에 이부분에서의 효과도 있을 것임.
- 그리고 6개 스레드의 경우 스레드가 물리 코어가 다 분리된 상태임. 그래서 내 스레드가 Top 멤버 변수 로컬에 저장하고 CAS할때 원자적으로 비교 및 캐시라인에 반영하면 다른 스레드가 도는 코어의 캐시 메모리는 무효화가 됨.
  그러면 그 스레드가 스냅샷 저장하고 cas할때의 처리 시간이 중간에 캐시메모리가 다른 캐시메모리에서 캐시라인 가져와야 하니 시간이 딜레이 될 것임.RHDD
- 그런데 스레드 갯수가 코어 갯수보다 많아지고 지금 하이퍼 스레딩 환경이기 때문에 l1 캐시메모리를 2개의 논리코어에 붙은 스레드가 공유할 수 있게 됨. 그러니 0번 물리 코어에 붙은 2개의 스레드 중 1개가 먼저 스냅샷 저장하려고
   캐시라인 가져와서 넣고 로컬에 스냅샷 저장하고 CAS성공하고 나서 0번 물리 코어에 붙은 다른 스레드가 또 스냅샷 저장할때 같은 L1 캐시메모리를 공유하니 굳이 다른 캐시 메모리에서 안긁어오고 바로 그냥 써버리니 오히려 스냅샷
   저장하고 CAS하는 시간이 더 빨라지니 성공률이 높아지는 원인이 될 수 있음.
