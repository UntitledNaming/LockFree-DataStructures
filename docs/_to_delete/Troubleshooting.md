# Troubleshooting

이 문서는 각 동시성 문제를 어떻게 발견하고 원인을 어디까지 좁혔는지를 정리합니다. "CAS128로 해결"처럼 결과만 적지 않고, 왜 그 해결이 필요한지와 로그로 어떻게 추적했는지를 남깁니다. 관련 자료는 `debug_cases/`와 `issues/`에 있습니다.

---

## 1. ABA 문제

- 증상: 태그 없는 CAS 스택을 여러 스레드로 돌리면, Pop 후 리스트가 깨지거나 이미 반환한 노드를 다시 반환하는(이중 반납) 상황이 발생.
- 초기 가설: Pop의 CAS 로직 자체가 잘못된 것으로 의심.
- 분석 과정:
  1. 크래시 순간의 상태만으로는 CAS가 왜 성공했는지 설명되지 않아, 각 스레드의 시도(지역 top/next, 스레드 ID, 순번)를 링 버퍼에 기록.
  2. 로그 시퀀스를 되짚으니, 스레드 A가 top과 top->next를 읽은 사이에 스레드 B가 그 노드를 Pop→반환→다시 Push해서 top이 A→B→A로 돌아온 시퀀스를 확인.
  3. A의 CAS는 주소가 같아 성공했지만, next는 이미 낡은 값이라 리스트가 어긋남을 확인.
- 원인: 주소만 비교하는 CAS가 "같은 주소 재사용"을 구분하지 못함.
- 해결: top 포인터에 단조 증가 버전 태그를 실어, 주소가 같아도 버전이 다르면 CAS가 실패하도록 함. 이 태그가 없으면 재사용을 구분할 방법이 없기 때문에 필요하다.
- 결과: 해결판이 같은 재현 시나리오를 손상 없이 통과.
- 배운 점: 동시성 버그는 상태 스냅샷이 아니라 이벤트 시퀀스를 추적해야 원인이 보인다.
- 관련 문서/로그: `issues/ABA/{reproduce,clear}/`, `debug_cases/ABA/`.

## 2. Page Decommit 문제

- 증상: 노드 페이지를 직접 관리하는 스택에서, 경쟁 Pop 중 다른 스레드가 접근 위반으로 크래시.
- 초기 가설: ABA와 같은 재사용 문제로 보고 버전 태그로 막으려 함.
- 분석 과정:
  1. 태그를 붙여도 크래시가 남는 것을 확인.
  2. 재현판이 마지막 노드 반환 시점에 페이지를 OS에 반환(`VirtualFree(MEM_DECOMMIT)`)하는 것을 확인.
  3. 스레드 A가 이미 top을 읽고 top->next를 역참조하려는 순간, 스레드 B가 페이지를 반환하면 A가 해제된 메모리에 접근함을 확인.
- 원인: ABA는 "같은 주소 재사용" 문제지만, 이건 "참조 중인 메모리가 OS에 반납되는" 문제. 버전 카운터는 메모리 생존 기간을 보장하지 못한다.
- 해결: 노드를 OS에 반환하지 않고 자체 메모리 풀에 보존·재사용해, 참조 중인 주소가 사라지지 않게 함. 즉 회수(reclamation)를 보류하는 정책이 필요했다.
- 결과: 자체 풀 해결판이 같은 시나리오를 크래시 없이 통과.
- 배운 점: 락프리는 "읽은 포인터가 언제든 유효"해야 하므로, 재사용뿐 아니라 메모리 회수 정책까지 함께 설계해야 한다.
- 관련 문서/로그: `issues/PageDecommit/{reproduce,clear}/`.

## 3. Order Reversal 문제

- 증상: 다중 스레드 큐에서 Enqueue 순서와 다르게 노드가 연결되거나 노드가 유실됨.
- 초기 가설: tail 전진(2nd CAS)이나 링크 CAS의 순서 문제로 의심.
- 분석 과정:
  1. 여러 케이스를 로그로 남겨 어떤 스레드가 어떤 순간에 tail/next를 읽고 CAS했는지 추적(`debug_cases/2nd CAS 실패 문제점 분석/`).
  2. 새 노드가 next=nullptr인 상태로 링크되는 도중, 다른 스레드가 tail의 next가 nullptr인 것을 보고 그 노드를 "완성된 꼬리"로 착각해 개입하는 시퀀스를 확인.
  3. 그 결과 삽입이 겹치며 순서가 뒤집히거나 노드가 유실됨을 확인.
- 원인: "tail의 next == nullptr"이 곧 "완성된 꼬리"를 뜻하지 않는다. 삽입 중 노드도 next가 nullptr이라 구분되지 않았다.
- 해결(1차): 삽입 중 노드의 next를 nullptr이 아닌 0xFFFF… 값으로 밀어 초기화하고, 다른 스레드가 그 값을 보면 대기(continue)하도록 함. 링크 성공 후에야 next를 nullptr로 확정. 이렇게 해야 삽입 중 노드를 남이 못 건드린다.
- 개선(태그 방식): 문제의 본질이 "내가 본 nullptr인지, 재사용 후 다시 만들어진 nullptr인지"의 구분이므로, next를 nullptr로 만들 때 상위 17비트에 발급 카운터(태그)를 실어 기록하고 1st CAS가 "내가 본 태그 붙은 nullptr"을 비교하게 함. 태그는 null 갱신 시에만 부여하면 충분하다(주소가 든 next는 어차피 비교 실패). → `include/LFQSingleTag.h`
- 결과: 해결판에서 순서 꼬임·유실이 사라짐.
- 배운 점: 공유 상태에서 "특정 값(nullptr)"에 두 가지 의미(완성/삽입 중)를 겹쳐 두면 안 된다. 삽입 중 상태를 명시해야 한다.
- 관련 문서/로그: `issues/OrderReversal/{reproduce,clear}/`, `debug_cases/2nd CAS 실패 문제점 분석/`.

## 4. Shared Node Pool 오염 문제

- 증상: 두 큐가 노드 풀을 공유할 때, 한 노드가 두 큐에 걸치거나 링크가 교차 오염됨.
- 초기 가설: 큐 각각의 CAS 로직 문제로 의심.
- 분석 과정:
  1. 노드 풀이 타입별 정적이라 두 큐가 같은 풀을 공유함을 확인.
  2. 큐1이 반환한 노드를 큐2가 재사용하는 중, 큐1의 tail CAS가 그 노드를 여전히 자기 것으로 보고 링크하는 시퀀스를 확인.
  3. 64비트 CAS는 next(주소)만 비교하므로 소유가 바뀐 것을 못 잡음을 확인.
- 원인: 링크 CAS가 노드의 소유(어느 큐 것인지)를 검증하지 않음.
- 해결(1차): 노드에 소유 큐 식별자(Qid)를 심고, 링크를 128비트 CAS로 바꿔 `(next==nullptr && Qid==내큐)`를 함께 검사. 남의 큐 노드면 CAS가 실패해 거부된다. 128비트 CAS가 필요한 이유는 포인터와 식별 정보를 원자적으로 함께 확인해야 하기 때문이다.
- 개선(태그 + 전역 발급): next의 nullptr에 태그를 싣는 방식을 공용 풀에 적용하되, 태그 발급 카운터를 큐별 멤버로 두면 서로 다른 큐가 우연히 같은 태그를 발급해 오인 삽입이 가능하다. 발급 카운터를 static 공용 변수로 만들어 모든 큐가 하나의 발급원을 공유하면 태그가 큐를 가로질러 유일해져 Qid 없이 64비트 CAS만으로 차단된다. 다만 전역 발급 카운터가 새 공유 캐시라인(경합 지점)이 되는 비용이 있어, 스레드 번호+스레드별 카운터 조합으로 개선할 수 있다. → `include/LFQMultiTag.h`
- 결과: 해결판에서 교차 오염이 사라짐.
- 배운 점: 자원을 공유하면 소유권 검증이 필요하고, 그 검증은 링크와 원자적으로 함께 이뤄져야 한다.
- 관련 문서/로그: `issues/SharedPool/{reproduce,clear}/`.
- 참고: "Enqueue 태그 불필요, Dequeue 필요"라는 초기 표현은 이후 번복되었다. Enqueue 자체의 ABA는 무해하지만, tail을 밀어주는 사전 작업에서 tail 변화 감지를 위해 TailCnt 태그가 필요함을 확인하고 태그를 다시 도입했다. 실제 코드 기준 정리는 `docs/Code_Flow.md` §6 참고.

## 5. 동기화 방식 비교 과정에서의 측정 이슈

- 증상: 방식별 처리량을 비교하는데, 조건에 따라 순위가 뒤집혀 "무엇이 더 빠른가"를 단정하기 어려움. 또한 초기 측정은 계측 카운터들이 캐시라인을 공유해 측정 자체가 경합을 오염시킴.
- 분석·조치:
  1. 스레드별 계측 카운터를 alignas(64)로 분리하고, interlock을 시도/성공/실패/무조건 RMW로 나눠 계측하도록 측정 프로그램을 정리한 뒤 전면 재측정(3분, 스레드 1/3/6/36, 물리 코어 어피니티).
  2. 재측정 결과 코어 이하 구간은 SRWLock ≫ Spinlock ≥ Lock-Free, 코어 초과(36스레드) 구간은 SRWLock > Lock-Free > Spinlock으로 역전됨을 확인.
  3. SRWLock의 경합 경로를 디스어셈블리로 확인하고 Spinlock에 같은 지수 백오프를 이식해 12억 → 46억 회복을 확인(원인 검증). 같은 백오프가 Lock-Free에는 효과가 없어 병목이 다름을 분리 검증.
- 원인: 성능은 절대 수치가 아니라 스레드/코어 비율·경합 구조·측정 조건에 좌우된다. 경합 비용의 실체는 공유 캐시라인이 코어 사이를 이동하는 동안 러닝 상태로 대기하는 시간이다.
- 해결: 비교 조건(스레드 수·시간·어피니티·계측 방식)을 명시하고, 조건별 결과와 원인 검증 실험을 함께 남김.
- 배운 점: 성능 비교는 절대 수치보다 비교 조건을 통제·명시하는 것이 더 중요하고, 계측 코드 자체도 경합 원인이 될 수 있다.
- 관련 문서/로그: `test/`, `docs/results/`, `docs/Test_Report.md`.

> 재현 테스트는 고의로 문제를 일으키는 코드이므로, 해결 테스트와 구분해 실행해야 합니다. 실행 방법은 `docs/Build_And_Run.md`를 참고하세요.
